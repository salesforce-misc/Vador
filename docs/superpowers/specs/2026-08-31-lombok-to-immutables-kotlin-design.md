# Lombok-to-Immutables Kotlin Migration Design

**Status:** Approved

**Date:** 2026-08-31

## Summary

Replace Lombok and the FreeFair delombok pipeline with Immutables 2.12.2 driven by KAPT. All
handwritten production source becomes Kotlin. Immutables continues to generate the public Java
configuration and specification classes so Java consumers retain the established fluent DSL.

The migration preserves Java source compatibility for supported consumer usage, but deliberately
does not preserve binary compatibility or Lombok-generated builder type signatures.

## Problem

Vador currently relies on Lombok `@SuperBuilder` across inherited configuration and specification
models. Kotlin compilation consumes delomboked Java rather than the normal source layout, and the
build contains Lombok-specific configuration in several places:

- the FreeFair Lombok Gradle plugin;
- a Kotlin source-set replacement with the `delombok` task output;
- an explicit `delombok` task configuration;
- a Lombok-only Sonar library configuration;
- `lombok.config` and IDE plugin instructions.

The repository has 18 production Java files, 17 of which use Lombok. Lombok also appears in test
fixtures. The generated builders form a public Java DSL, so replacing annotations with ordinary
Kotlin data classes would remove required builder behavior and introduce substantial handwritten
code.

## Goals

- Remove Lombok, FreeFair Lombok, delombok, and every operational Lombok reference from source,
  build configuration, tests, and user-facing documentation. This historical design record is the
  sole allowed reference after migration.
- Make every handwritten production source file Kotlin.
- Preserve the documented Java DSL, getters, immutable-value behavior, and `toBuilder()` workflow.
- Generate storage, builders, collection handling, equality, hashing, and immutable implementations.
- Use standard Kotlin/KAPT and Gradle source layouts without compiler source-set substitution.
- Publish useful binary, source, and Javadoc artifacts.
- Preserve the repository's existing Gradle, Kotlin, JDK, plugin, dependency, wrapper, and SDK
  versions except for adding Immutables 2.12.2 and the matching Kotlin KAPT plugin declaration.

## Non-goals

- Binary compatibility with consumers already compiled against Lombok-generated bytecode.
- Compatibility with explicit references to Lombok-generated builder class names or generic
  signatures.
- Supporting consumer subclasses of the public `Base*` model hierarchy.
- Preserving reflective assumptions about constructors or the exact intermediate superclass.
- Preserving the exact generated `toString()` text format.
- Preserving a Java serialization format; the model hierarchy does not currently use Java
  serialization.
- Replacing KAPT with a new project-owned KSP code generator.

## Decision

Use all-Kotlin abstract model declarations with Immutables 2.12.2 through KAPT.

Kotlin abstract base classes retain shared state declarations and behavior. Immutables input types
use an `Abstract*` name and generate the existing public class name:

| Handwritten Kotlin input | Generated public class |
|---|---|
| `AbstractValidationConfig` | `ValidationConfig` |
| `AbstractBatchValidationConfig` | `BatchValidationConfig` |
| `AbstractSpec1` | `Spec1` |
| `AbstractSpec2` | `Spec2` |

The same pattern applies to the remaining configuration, container, and specification types.
Generated implementations remain final and extend the handwritten abstract input, which in turn
extends the appropriate public Kotlin base class.

The `Abstract*` inputs are generator-facing types rather than supported consumer API. Kotlin marks
them `internal`; they remain JVM-visible because Kotlin has no package-private top-level classes.

## Alternatives considered

### Java model island with javac annotation processing

This is the simplest and most stable Immutables integration because it avoids KAPT, but it retains
a handwritten Java island and conflicts with the preference for an all-Kotlin implementation.

### Handwritten Kotlin builders

This avoids annotation processing but duplicates a large generated surface across generic
hierarchies. It would create the maintenance burden this migration is intended to remove.

### Project-owned KSP generator

KSP is Kotlin-first, but Vador would own a custom processor for builder inheritance, singular
methods, nullability, copying, and Java signatures. That is substantially more maintenance and risk
than using an established generator.

## Source model

### Kotlin properties and Java getters

Model attributes are idiomatic abstract Kotlin properties. KAPT exposes them as JavaBean methods,
which Immutables implements on the generated class:

```kotlin
abstract class BaseValidationConfig<ValidatableT, FailureT> {
  abstract val withSpecs: List<Spec<ValidatableT, FailureT>>
}
```

Java consumers continue to call `getWithSpecs()`, while handwritten Kotlin uses `withSpecs`.

Zero-argument behavioral methods are marked `@Value.NonAttribute` so the processor never treats
them as stored attributes. Base types remain abstract classes rather than interfaces: with Vador's
current JVM-default settings, Kotlin interface bodies compile through `DefaultImpls`, which a
generated Java implementation does not inherit.

### Generation styles

Two Kotlin meta-annotations define the public DSL:

| Model family | Builder entry point | Terminal method |
|---|---|---|
| Configuration | `toValidate()` | `prepare()` |
| Specification | `check()` | `done()` |

Both styles configure:

- `typeAbstract = ["Abstract*"]` and `typeImmutable = "*"`;
- `toBuilder = "toBuilder"`;
- JavaBean getter recognition;
- collection and map singular generation;
- public generated implementations.

Every value type uses `@Value.Immutable(copy = false)`. This suppresses Immutables' additional
`copyOf` and `withX` API while retaining the required `toBuilder()` method.

### Legacy singular aliases

Immutables mechanically handles the ordinary trailing-plural singulars and aliases whose current
singular name already equals the attribute name. It cannot infer compound Lombok aliases whose
plural word appears in the middle of an attribute name.

Fifteen unique aliases require compatibility methods:

1. `shouldHaveFieldOrFailWith`
2. `shouldMatchField`
3. `shouldMatch`
4. `matches`
5. `shouldRelateWithEntry`
6. `orField1ShouldMatch`
7. `orField2ShouldMatch`
8. `whenFieldMatches`
9. `thenFieldShouldMatch`
10. `shouldHaveValidFormatOrFailWith`
11. `absentOrHaveValidFormatOrFailWith`
12. `shouldHaveValidSFIdFormatOrFailWith`
13. `shouldHaveValidSFPolymorphicIdFormatOrFailWith`
14. `absentOrHaveValidSFIdFormatOrFailWith`
15. `absentOrHaveValidSFPolymorphicIdFormatOrFailWith`

Small generic Kotlin builder contracts centralize these aliases. The generated builder implements
the underlying initializer, and a default method delegates the legacy name to it:

```kotlin
interface ValidationBuilderDsl<ValidatableT, FailureT, SELF> {
  fun shouldHaveFieldsOrFailWith(
    key: TypedPropertyGetter<ValidatableT, *>?,
    failure: FailureT?,
  ): SELF

  fun shouldHaveFieldOrFailWith(
    key: TypedPropertyGetter<ValidatableT, *>?,
    failure: FailureT?,
  ): SELF = shouldHaveFieldsOrFailWith(key, failure)
}
```

Each Immutables input declares only the relevant abstract nested builder and its reusable DSL
contracts. Immutables still generates the builder's storage, bulk methods, regular initializers,
terminal method, and copy logic.

### Nullability and collections

- Lombok `@NonNull` becomes a non-null Kotlin type.
- JetBrains `@Nullable` becomes `T?`.
- Singular collections and maps are non-null and default to empty.
- Container entries that permit null use a source-retained Kotlin `@AllowNulls` getter annotation,
  which Immutables recognizes by simple name.
- Built collections and maps remain immutable snapshots.

The feasibility probe verified nullable scalar values, nullable map keys and values, inherited
generic attributes, JavaBean accessors, and independent `toBuilder()` copies.

## Java source-compatibility contract

The migration preserves:

- public packages, generated class names, and generic type parameters;
- `Type.<...>toValidate()...prepare()`;
- `Type.<...>check()...done()`;
- `value.toBuilder()` followed by the appropriate terminal method;
- existing JavaBean getters;
- bulk collection/map initializers and all 35 existing singular methods;
- public base-class assignability and inherited helper behavior;
- value-based `equals` and `hashCode` behavior;
- an informative generated `toString()`, without treating its exact text format as API;
- existing domain validation methods and messages.

Generated nested builder types will change to Immutables builder types. Internal Vador code must use
type inference or the new generated builder types rather than expose them as stable API.

## Failure semantics

Explicit null passed to a non-null initializer still fails immediately. Existing domain validation
rules and exception messages remain unchanged.

One approved generator-level difference remains: if a required attribute is omitted entirely,
Lombok eventually throws `NullPointerException`, while Immutables rejects the incomplete builder
with `IllegalStateException`. No current test or documentation depends on the exact exception class.
Recreating it would require handwritten checks for every mandatory attribute and is intentionally
out of scope.

## Gradle and publishing design

Add version-catalog entries for Immutables 2.12.2 and Kotlin KAPT. The `vador` module uses:

```kotlin
kapt(libs.immutables.value)
compileOnly(libs.immutables.value.annotations)
```

Immutables is therefore not a runtime dependency and must not appear in the published runtime POM.
Set `kapt.use.k2=true`, matching the established ReVoman setup. The current processor reports that
K2 KAPT is alpha and that the processor is non-incremental; these warnings are accepted and covered
by the compatibility gates below.

Remove:

- the FreeFair Lombok plugin and catalog entries;
- the root Lombok import and Sonar-only Lombok configuration;
- the `delombok` task and Kotlin source-set replacement;
- `lombok.config`;
- Lombok IDE instructions and all remaining operational Lombok mentions.

Handwritten production files live under `vador/src/main/kotlin`. Java consumer-contract fixtures
remain under `vador/src/test/java` intentionally.

Gradle's default `sourcesJar` does not include KAPT-generated Java. The `sourcesJar` and `javadoc`
tasks must depend on KAPT generation and include `build/generated/source/kapt/main`, so published
artifacts contain navigable source and API documentation for generated public classes.

Generated code is excluded from coverage and static-analysis debt using
`org.immutables.value.Generated`, following the ReVoman convention.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| K2 KAPT is alpha and Immutables reports non-incremental processing | Pin Kotlin and Immutables versions; cover clean and configuration-cache builds |
| Immutables marks styled `toBuilder()` as experimental | Pin Immutables 2.12.2 and compile the exact Java copy workflow in contract tests |
| Kotlin builder contracts refer to generated builder self-types | Keep the pattern small and uniform; compile both Kotlin and Java consumers in CI |
| Kotlin `internal` generator inputs remain JVM-visible | Treat `Abstract*` types as unsupported implementation detail and do not use them in documented APIs |
| Default sources JAR omits generated Java | Make source and Javadoc artifacts depend on KAPT and include its generated-source directory |

## Migration sequence

The implementation occurs on one branch in reviewable stages. Lombok and Immutables may coexist
temporarily during development, but no final or released state contains a partially migrated model
family.

1. Add Java source-compatibility tests and record the current behavior.
2. Add Immutables styles, compatibility builder contracts, and temporary KAPT wiring.
3. Migrate `BaseSpec`, `Spec1` through `Spec5`, `SpecFactory`, and internal specification builder
   references atomically.
4. Migrate the complete configuration hierarchy and all internal configuration builder references
   atomically.
5. Convert Lombok-based test fixtures to Kotlin equivalents.
6. Remove Lombok, delombok, Sonar workarounds, IDE instructions, and temporary dual-processor
   configuration.
7. Run the complete verification matrix and a final zero-match operational Lombok search, excluding
   this historical design record.

## Verification

| Gate | Required evidence |
|---|---|
| Java DSL | Compile and run unchanged-style Java contract fixtures |
| Kotlin usage | Compile same-source Kotlin consumers of generated classes |
| Singular compatibility | Exercise all 35 singular methods, including the 15 aliases |
| Copying | Verify `toBuilder()` produces an independent immutable copy |
| Inheritance | Exercise inherited generic attributes across config and spec families |
| Nullability | Verify nullable scalars and allowed null collection/map entries |
| Behavior | Run `:vador:test` and the repository `check` task |
| Generated API | Inspect factories, getters, singulars, and `toBuilder()` with `javap` |
| Publishing | Build binary, sources, Javadoc JARs, and generated POM |
| Dependency hygiene | Confirm no Lombok or runtime Immutables dependency is published |
| Build hygiene | Run a clean, configuration-cache-compatible build |
| Removal | Require binary-excluded `git grep -I -i lombok -- ':!docs/superpowers/specs/2026-08-31-lombok-to-immutables-kotlin-design.md'` to return zero matches |
| Worktree | Finish with only the intended committed migration |

## Feasibility evidence

An isolated Gradle probe used Vador's Kotlin 2.1.10, Gradle 8.14.1 wrapper, JDK 17 toolchain, and
Immutables 2.12.2. It compiled and ran both Kotlin and Java consumers and verified:

- two generated concrete configuration subtypes sharing a Kotlin abstract base hierarchy;
- `toValidate()`/`prepare()` and `check()`/`done()` naming;
- `toBuilder()` with independent collection copies;
- ordinary and custom map/collection singular methods;
- nullable scalars, map keys, and map values;
- inherited Kotlin helper methods;
- JavaBean getters generated from abstract Kotlin properties;
- `copy = false` suppressing `copyOf` and `withX` while retaining `toBuilder()`.

The first probe also identified and resolved two design traps:

1. compound Lombok singular aliases require explicit reusable builder-contract methods;
2. Kotlin abstract base classes must be used for inherited concrete behavior under Vador's current
   JVM-default compiler settings.
